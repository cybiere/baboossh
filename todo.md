# Known bug: Connection.identify() stores shell error text as real field data

`Connection.identify()` (`baboossh/connection.py`) only checks the exit code of the `hostname` command; the exit codes of `uname -a`, `cat /etc/machine-id`, and the MAC-gathering pipeline are ignored, and their raw `result` string is stored regardless of success. On a host without `/etc/machine-id` (common on non-systemd distros), `cat /etc/machine-id` fails and its stderr text (e.g. `"cat: /etc/machine-id: No such file or directory"`) gets silently stored as `Host.machine_id`, rather than being treated as empty/absent. Doesn't crash `identify()` but corrupts that field's meaning. Fix: check each command's exit code like `hostname` already does, and store `""`/`None` on failure instead of the error text.

# Known limitation: paramiko has no ChaCha20-Poly1305 support — baboossh cannot reach ChaCha20-only SSH servers

`paramiko`'s cipher list (`paramiko.transport.Transport._preferred_ciphers`) doesn't implement `chacha20-poly1305@openssh.com` at all. TinySSH implements *only* that cipher, so there is zero overlap and `baboossh` can never connect to a stock TinySSH server, or any SSH server restricted to ChaCha20-Poly1305 only. Not fixable via `baboossh`'s own config (would need a paramiko-side cipher implementation or switching SSH libraries). `tests/docker/` deliberately includes a ChaCha20-only container so this failure mode is exercised.

The actual failure mode is an **uncaught** `paramiko.ssh_exception.IncompatiblePeer` propagating out of `Workspace.probe()` — `Connection.probe()` only catches `(TimeoutError, OSError, ConnectionRefusedError)`, not `paramiko.SSHException`. Neither `Workspace.probe()` nor the `do_probe`/`do_connect` shell commands catch it, so this surfaces as an unhandled traceback rather than the "OK"/"KO" style clean failure `probe()` gives for a plain refusal/timeout. Arguably `probe()` should catch `paramiko.SSHException` alongside its existing catches. Not fixed.

# Possible UX issue: Workspace.probe() is very slow against a genuinely unreachable host

`probe()` against a host with no known/discoverable path took over 2 minutes before being killed (never finished). `probe()`'s fallback chain (`baboossh/workspace/probe.py`) tries several strategies in sequence — direct, given gateway, existing path, direct-from-local, then *every known `Host`* as a candidate gateway — each needing its own full connection timeout before falling through. Against a genuinely unreachable target, every attempt times out, so total wait scales with the number of known hosts. Not a bug (no incorrect behavior, just slow), but worth a look — e.g. shorter timeouts for exploratory fallback attempts, or surfacing progress/cancellation.
