# Known bug: Connection.identify() stores shell error text as real field data

`Connection.identify()` (`baboossh/connection.py`) only checks the exit code of the `hostname` command; the exit codes of `uname -a`, `cat /etc/machine-id`, and the MAC-gathering pipeline are ignored, and their raw `result` string is stored regardless of success. On a host without `/etc/machine-id` (common on non-systemd distros), `cat /etc/machine-id` fails and its stderr text (e.g. `"cat: /etc/machine-id: No such file or directory"`) gets silently stored as `Host.machine_id`, rather than being treated as empty/absent. Doesn't crash `identify()` (found while designing a Docker test range covering non-systemd targets, where this would otherwise go unnoticed) but corrupts that field's meaning. Fix: check each command's exit code like `hostname` already does, and store `""`/`None` on failure instead of the error text.

# Known limitation: paramiko has no ChaCha20-Poly1305 support — baboossh cannot reach ChaCha20-only SSH servers

Confirmed empirically while building the Docker test range (`tests/docker/`): `paramiko` 5.0.0's cipher list (`paramiko.transport.Transport._preferred_ciphers`) is AES-CTR/AES-CBC/3DES/AES-GCM only — it does not implement `chacha20-poly1305@openssh.com` at all. TinySSH deliberately implements *only* that cipher (no AES, by design — see its man page), so there is zero cipher overlap and `baboossh` can never connect to a stock TinySSH server, or to any other SSH server restricted to ChaCha20-Poly1305 only. This isn't fixable via `baboossh`'s own config — it would need either a paramiko-side cipher implementation (out of this project's control) or switching SSH libraries, neither of which is proposed here. Tracked as a known target-compatibility gap; the test range deliberately includes a ChaCha20-only container (reachable, not hidden behind a pivot) specifically so `baboossh`'s failure mode against it is itself something to verify and, if needed, improve.

Confirmed via `tests/test_docker_range.py::test_incompatible_ssh_server_fails_cleanly`: the actual failure mode is an **uncaught** `paramiko.ssh_exception.IncompatiblePeer` propagating all the way out of `Workspace.probe()`. `Connection.probe()` (`baboossh/connection.py`) only catches `(TimeoutError, OSError, ConnectionRefusedError)` around `open_transport()`; a cipher/kex/host-key mismatch raises a `paramiko.SSHException` subclass instead, which isn't one of those. Neither `Workspace.probe()` nor the `do_probe`/`do_connect` shell commands catch it either, so in the interactive shell this currently surfaces as an unhandled traceback rather than the "OK"/"KO" style clean failure message the rest of `probe()` gives for a plain connection refusal or timeout. It's still a specific, clear exception (not a hang, not something generic) rather than the failure being silent — but arguably `probe()` should catch `paramiko.SSHException` alongside its existing catches and report it the same way. Not fixed here.

# Possible UX issue: Workspace.probe() is very slow against a genuinely unreachable host

Confirmed while exercising the Docker test range's fully-firewalled "unreachable" container: `probe()` against a host with no known/discoverable path took over 2 minutes before I killed it (it never finished). `probe()`'s fallback chain (`baboossh/workspace/probe.py`) tries several strategies in sequence — direct, given gateway, existing path, direct-from-local, then *every known `Host`* as a candidate gateway — and each attempt needs its own full connection timeout before falling through to the next. Against a target that's truly unreachable, every one of those attempts times out rather than failing fast, so the total wait scales with the number of known hosts. Not confirmed as a bug (no incorrect behavior, just slow), but worth a look — e.g. shorter timeouts for the exploratory fallback attempts, or surfacing progress/allowing cancellation, so `probe()` on an unreachable target doesn't feel like a hang.

- **The `Unique` metaclass** (`utils.py`) — not typed. Metaclass typing (`__call__`/`__new__` interacting with per-workspace instance caching) is inherently advanced; `Self` usage in the classes that use it as their metaclass works fine without this.
- **Full `mypy`/`pyright` CI enforcement** — hints were added and spot-checked file-by-file (`pyright` reports 0 errors on `baboossh/workspace/`; `mypy` isn't installed in this environment so only spot-checked historically), but no CI gate was wired up. Doing so now would likely still fail on `shell/`'s untyped state and on genuinely unfixable noise (no type stubs exist for `paramiko`/`tabulate`).
- **CRUD base-class extraction** (the original audit finding this work was scoped down from) — still deferred, still gated on adding tests for `Host`/`Endpoint`/`User`/`Creds`/`Connection` first (see "Testing follow-up" above).

## `workspace/` typing — closed

All 11 mixin files now have full type hints, following the `Self`/native-union/`TYPE_CHECKING` conventions already established for the model classes, with one addition specific to this package: **mixin `self` parameters can't be annotated with the concrete `Workspace` class** (pyright rejects it — `Workspace` is a *subclass* of each mixin, not a supertype, and pyright requires an explicit `self` annotation to be a supertype of the enclosing class). Instead, each mixin file defines a small local `Protocol` under `TYPE_CHECKING` listing only the `Workspace` attributes/methods that file actually uses (`options`, `tunnels`, `workspace_folder`, `unstore`, `set_option`, `probe`, `path_del`, as needed), and annotates `self` with that Protocol — structural typing sidesteps the nominal-supertype rule cleanly. `pyright baboossh/workspace/` went from 56 errors to 0.

Adding tests first (before typing, per the plan this section originally set) surfaced **9 real, previously-unknown bugs**, all now fixed with regression tests in `tests/test_workspace_*.py`:
1. `hosts.py` `host_del` — missing `None`-check on `Host.find_one()` (defensive; practically unreachable given the membership check just above it).
2. `paths.py` `path_find_existing` — same missing-`None`-check pattern.
3. `paths.py` `path_find_existing` — `chain[0] = "local"` mutated a `list[Host | Endpoint | None]` with a `str`; refactored into a separate `labels: list[str]` built via list comprehension, output unchanged.
4. `probe.py` `probe()` — an unknown/typo'd gateway host name crashed with `AttributeError` instead of a clean error; now prints and returns cleanly.
5. `probe.py` `probe()`'s `host` variable — pyright flagged it "possibly unbound"; traced by hand and confirmed not a live bug (a prior unconditional assignment always covers every path that reaches the use site) — added a no-op `host: "Host | None" = None` initializer purely to satisfy the type checker.
6. `tunnels.py` `tunnel_open` — `Connection.from_target()` returning `None` was passed straight into `Tunnel()`, which requires a non-`None` connection; now checked and reported cleanly.
7. `tunnels.py` `tunnel_close` — **the one real, reachable bug of the batch**: printed "No tunnel on port X" but then fell through to `self.tunnels.pop(port)` with no `default=`, raising an uncaught `KeyError` right after the "clean" error message. Missing `return`. Caught by a test crashing at workspace-fixture teardown before the fix.
8. `options.py` `set_option` — `set_option("connection", None)` cleared and printed the three connection options but fell through (missing `return`) into `Connection.from_target(None)`, crashing with `TypeError`. Caught immediately on first test run.
9. `connections.py` `enum_run` — the `!tagname` branch built an unused `endpoints = tag.endpoints` (plural) instead of assigning the `Tag` object to the `endpoint` variable actually passed to `Connection.find_all(endpoint=endpoint, ...)`, which accepts `Endpoint | Tag | None`; a target like `"user:cred@!tagname"` left `endpoint` as the raw string `"!tagname"` instead. Found while widening the variable's type annotation during the typing pass (not by pyright directly, and not part of the original 56-error baseline).
